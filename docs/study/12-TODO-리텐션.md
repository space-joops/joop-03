## Q13. 자동 수거 정산 수술 ⭐⭐⭐ — 방치형의 심장 고치기 (#31)

**왜**: `settleIdleCollection`(`lib/space.ts`)은 방치 보상의 전부인데 결함이 셋 겹쳐 있습니다: ① `last_collected_at` 이 null 이면 **영원히 자동 수거가 시작되지 않음**(발사 직후 계정이 여기 해당할 수 있음) ② 동시 요청 시 중복 적립(낙관적 가드 미적용 — 저장소에서 유일하게) ③ **"음영 지역에서 자동 수거"라는 안내 문구와 달리 실제로는 음영을 보지 않음**(#31-5). 약속과 다른 보상은 신뢰를 깎습니다.

**파일**: `lib/space.ts`, `app/[lang]/joop/map/page.tsx`(호출 위치 — 렌더 본문에서 DB 쓰기 중, #31-2), dict(정산 안내 문구).

**힌트**:
1. **null 함정**: 발사 완료(`completeLaunch`)에서 `last_collected_at = now` 를 심는 것이 근본 치료입니다. 기존 null 계정을 위한 방어(정산 시 null 이면 now 로 초기화하고 0 적립)도 함께.
2. **중복 적립**: `submitArcadeResult` 의 낙관적 동시성 루프(`.eq("total_collected", base)` + 갱신 행 확인 + 재시도)를 그대로 이식하세요 — 04 문서 §5, 저장소에 선례 3곳.
3. **음영 판정**: 이제 `shadowStateAt`(`lib/orbit.ts`)이 있으니 마지막 정산 시각~현재 사이에서 음영이었던 시간 비율을 구해 곱하면 됩니다. 음영 모델이 위상 사인파라(05 문서 §4) 구간 내 음영 시간도 해석적으로 계산 가능 — 근사(비율 = shadow_fraction)로 시작해도 충분합니다.
4. **12시간 상한의 가시화**: 지금은 24시간 만에 와도 12시간분만 조용히 적립됩니다(#31-3). "12시간 상한, 가득 참!" 문구가 손실을 성취("가서 비워야지")로 바꿉니다.

**검증**: 프리뷰에서 null 계정 시나리오, 연타 요청(중복 방지), 정산 문구. 워크로그에 정산 규칙 표를 남기세요 — 이 퀘스트는 게임 경제의 문서화 가치가 큽니다.

## Q14. 주간 등락을 진짜로 움직이게 ⭐⭐ (#33-1)

**왜**: 첫 화면 랭킹의 ▲▼ 등락은 `prev_rank`(7일 전 누적 기준)인데, NPC 100개의 수거 이력이 시드 시점 고정이라 **등락이 영원히 "–"** 입니다. 지표가 안 움직이면 "함께 청소하는 세계"라는 세계관의 증거가 죽어 있는 셈입니다.

**파일**: `supabase/migrations/`(NPC 활동 시뮬레이션) 또는 서버 크론 대체물, `joop_03_debris_events`.

**힌트**:
1. 가장 단순한 접근: NPC 들에게 **매일 소량의 debris_events 를 흘려 넣는** 것. 별도 크론이 없으므로, 첫 화면 서버 조회 시 "오늘자 NPC 이벤트가 없으면 생성"하는 지연 시드(lazy seed)가 현실적입니다 — `settleIdleCollection` 이 이미 "조회 시 정산" 패턴의 선례.
2. NPC 별 활동량은 결정적으로: `starHash(npcIndex, dayOfYear, 0)` 기반이면 서버 인스턴스가 몇 개든 같은 값(05 문서 §7). 삽입 자체는 유니크 제약(joop_id+날짜)으로 멱등하게.
3. #46(NPC 삭제 논의)과 방향을 맞추세요 — "NPC 를 지우면 화면이 빈다"는 딜레마가 이슈에 기록돼 있습니다. NPC 를 살리는 쪽이라면 이 퀘스트가 그 근거가 됩니다.

**함께 열리는 것**: 이게 되면 `components/sparkline.tsx`(지금은 데이터가 시계열이 아니라 뺐음 — 컴포넌트는 살아 있음)를 일별 집계 뷰로 되살릴 수 있습니다. 뷰 작성은 `joop_03_rankings_weekly` 가 교본.

## Q15. 재방문 훅 1단계 — 부재중 보고서 ⭐⭐

**왜**: 돌아온 사용자에게 "당신이 없는 동안"을 말해주는 화면이 없습니다. 정산은 조용히 일어나고, 사용자는 자기가 뭘 얻었는지 모릅니다. **부재중 보상의 가시화는 방치형 리텐션의 표준 장치**입니다.

**파일**: `app/[lang]/joop/map/page.tsx`(정산 결과가 이미 반환값으로 있음 — `settleIdleCollection(): number`), 신규 오버레이 컴포넌트, dict.

**힌트**:
1. 정산량이 0 보다 크면 지도 진입 시 1회 오버레이: "부재중 줍스가 N 조각을 수거했어요" + 줍스 스프라이트(collect 프레임) + 확인 버튼. 연출 선례는 아케이드 saved 오버레이.
2. "1회만"은 이 저장소의 1회성 신호 관용구(`?setup=done` 스타일 쿼리 또는 세션 스토리지)로.
3. Q13(음영 정산)과 합치면 "음영 구간에서 N 조각"으로 문구가 더 세계관다워집니다.

**다음 단계 예고(별도 퀘스트로)**: 웹 푸시(FR-6.6). ADR-0002 가 "시점 미정"으로 남겨둔 VAPID 푸시 — 서비스워커가 없어서 큰 공사입니다. 부재중 보고서로 효과를 먼저 검증하고 가세요.

## Q18. 피초대자 추적·보상 ⭐⭐⭐ (FR-9.2 — 성장 루프의 완성)

**왜**: 광고 도킹으로 초대코드가 발급되기 시작했고 `issuer_id` 도 쌓입니다. 하지만 **초대한 사람이 얻는 것이 없습니다.** "내 코드로 3명이 가입했고 나는 보상을 받았다"가 되어야 코드가 공유될 이유가 생깁니다 — 리텐션과 신규 유입을 한 번에 무는 퀘스트.

**파일**: `app/[lang]/onboarding/actions.ts` 의 `redeemInvite`(`redeemed_by` 는 이미 기록됨!), 인벤토리 또는 대시보드에 "내 초대 현황", 보상 지급 액션.

**힌트**:
1. 데이터는 이미 다 있습니다: `invite_codes.issuer_id`(누가 발급) + `redeemed_by`(누가 사용). 조회 하나로 "내 코드로 가입한 줍스 목록"이 나옵니다.
2. 보상 설계(작게): 피초대자가 **첫 궤도 진입**에 도달하면 발급자에게 수거 조각 보너스 — "가입"만으로 주면 어뷰징이 쉽습니다. 지급 멱등성(중복 지급 방지)은 지급 기록 테이블 또는 `invite_codes` 에 `rewarded_at` 컬럼(마이그레이션 1개).

**⚠️ 함정**: `redeemInvite` 에는 경쟁 조건 이슈(#30)가 있습니다 — 이 퀘스트를 하기 전에 13 문서의 해당 퀘스트를 먼저 처리하는 것이 안전합니다(보상이 걸리면 어뷰징 가치가 생기므로).
