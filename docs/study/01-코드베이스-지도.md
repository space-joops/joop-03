# 01. 코드베이스 지도 — 무엇이 어디에 있나

> 새 코드베이스에서 길을 잃지 않는 가장 빠른 방법은 **사용자의 여정을 따라 파일을 배치해 보는 것**입니다.
> 이 문서는 게임 한 판의 흐름 위에 라우트·컴포넌트·lib·DB 를 겹쳐 그린 지도입니다.

## 1. 게임 한 판의 여정 = 코드의 배치도

```
[온보딩]         [지상 훈련]        [발사 청약]      [발사 중계]        [궤도 생활]
초대코드 입력  →  낙하물 받기    →  발사체 선택  →  카운트다운~사출  →  지구본·자동수거
/onboarding      /joop/train       /launch          /joop/launch        / (첫 화면), /joop/map
    ↓                ↓                 ↓                 ↓                    ↓
redeemInvite     ground-minigame   launch-list      launch-sequence     orbital-canvas
(서버 액션)       (클라 캔버스)      (서버+폼)         (클라 캔버스)        orbit-track-map
    ↓                ↓                 ↓                 ↓                    ↓
invite_codes     debris_events     launch_bookings  joops.status        joops(궤도 파라미터)
profiles         joops.xp          launch_vehicles  ground→queued→orbit  debris_events
                                                                             ↓
                                                    [아케이드]           [인벤토리]
                                                    우주에서 수거     →   수집·도킹 확인
                                                    /joop/arcade         /joop/inventory
                                                    arcade-game          inventory-view
                                                    debris_events        localStorage 만!
                                                    invite_codes(도킹보상)
```

이 흐름에서 **줍스(로봇)의 상태 머신**이 모든 페이지 가드를 결정합니다:

```
ground ──(레벨 달성+청약 확정)──> queued ──(발사 시퀀스 완료)──> orbit ──(지구 복귀)──> ground
```

`joop_03_joops.status` 컬럼이 진실이고, 각 페이지는 서버에서 이 상태를 확인해 리다이렉트합니다
(예: `app/[lang]/joop/launch/page.tsx` — orbit 이면 지도로, queued 가 아니면 대시보드로).
⚠️ DB 체크 제약에는 `launching` 상태도 있지만 **코드는 아직 안 씁니다**(이슈 #36-4, 퀘스트 11 참고).

## 2. app/ — 라우트 트리

Next.js App Router 는 **폴더 구조 = URL 구조**입니다. `[lang]` 은 동적 세그먼트(en/ko).

| 경로 | 역할 | 서버 가드 |
|---|---|---|
| `app/[lang]/page.tsx` | 첫 화면(공개 궤도 대시보드). 5개 서버 조회를 `Promise.all` 로 병렬 실행 후 클라 셸에 props 주입 | 없음(공개) |
| `app/[lang]/layout.tsx` | 게임 루트 레이아웃 — GTM, 폰트, OG 메타데이터, 스플래시, PWA 배너, `body.crt-scanlines` | — |
| `app/[lang]/onboarding/` | 초대코드 입력 / 이메일 대기리스트 (`?code=` 쿼리로 코드 프리필) | 이미 분양받았으면 홈으로 |
| `app/[lang]/onboarding/setup/` | 이름(유니크)·색(6색) 설정 | 세션 없으면 온보딩으로 |
| `app/[lang]/joop/page.tsx` | 내 줍스 대시보드 — status 3분기 CTA + 인벤토리 버튼(분기 밖 공통) | 줍스 없으면 온보딩으로 |
| `app/[lang]/joop/train/` | 지상 훈련 미니게임 | ground 전용 |
| `app/[lang]/launch/` | 발사체 청약 목록 | — |
| `app/[lang]/joop/launch/` | 발사 시퀀스(카운트다운→중계→사출) | **queued 전용** (3단 리다이렉트) |
| `app/[lang]/joop/launch/replay/` | 발사 다시 보기 | **없음** — localStorage 만 읽으므로 |
| `app/[lang]/joop/map/` | 우주 지도(지구본+궤적 모니터+자동수거 정산) | orbit 전용 |
| `app/[lang]/joop/arcade/` | 우주 수거 아케이드(풀블리드) | orbit 전용, 음영이면 XP 게이트 오버레이 |
| `app/[lang]/joop/inventory/` | 인벤토리 | **없음** — localStorage 만 |
| `app/[lang]/rankings/` | 전체 랭킹(100행) | 없음(공개) |
| `app/admin/**` | 관리자 콘솔(로케일 없음, 한국어 고정) | 3층 가드(아래 §6) |
| `app/api/orbital/route.ts` | 궤도 스냅샷 API — CDN `s-maxage` 를 관리자 설정값으로 동적 발급 | — |
| `app/api/version/route.ts` | 버전 조회(no-store) — PWA 업데이트 감지 채널 | — |

특이점 둘:
- **루트 `app/layout.tsx` 가 없습니다.** `[lang]`(게임)과 `admin` 이 각각 `<html>` 을 렌더하는 **다중 루트 레이아웃** 구조 — 관리자에 게임용 스플래시·스캔라인·GTM 을 태우지 않기 위해서입니다(`app/admin/layout.tsx` 주석).
- 게임 페이지 대부분이 `export const dynamic = "force-dynamic"` — ① 매 요청 신선한 스냅샷 ② "화면에 다시 들어오면 최신 관리자 설정이 반영된다"(FR-10.2)는 게임 규칙의 구현입니다.

## 3. lib/ — 세 개의 층

lib 는 **import 방향으로 세 층**이 나뉩니다. 이 구분이 이 코드베이스에서 가장 중요한 설계입니다.

### ① 순수 계층 (서버·클라 어디서든 import 가능, 부수효과 0)

| 파일 | 담당 |
|---|---|
| `lib/orbit.ts` | 궤도 역학의 심장 — `positionAt`(3D 위치), `shadowStateAt`(음영 판정 해석해), `groundStateAt`(위경도) |
| `lib/arcade.ts` | 아케이드 물리 — `applyThrust`(관성), `joystickInput`(5원 조이스틱), `collides`, `starHash`(시드 난수), `CELESTIALS`(천체 배치) |
| `lib/minigame.ts` | 지상 훈련 규칙 — 낙하 속도/간격 곡선, `bondFrom`(유대), `levelFromXp` |
| `lib/vehicle-profiles.ts` | 발사체 프로필 + 발사 타임라인 + 텔레메트리 곡선(smoothstep) |
| `lib/ad-satellites.ts` | 광고 위성 6종 하드코딩 + 1/z 원근 플라이바이(`makeFlyby`/`flybyPose`) |
| `lib/joop-sprite.ts` | 스프라이트 시트 계약(프레임·fps·색 매핑) |
| `lib/orbit-clock.ts` | 가상 시계 — Δt×배속 누적(배속 변경 시 위상 점프 방지) |
| `lib/config-specs.ts` | 관리자 설정 29키 레지스트리(타입·범위·폴백의 단일 진실) |

**왜 순수 계층인가**: 같은 함수를 서버(API 라우트·서버 컴포넌트)와 클라(캔버스 보간)가 **동일하게 import** 해서, "서버가 말한 위치"와 "클라가 그린 위치"가 절대 어긋나지 않습니다. 데이터 엔지니어링으로 치면 **변환 로직을 한 곳에 두고 배치·스트리밍이 공유**하는 것과 같습니다.

### ② 서버 계층 (`import "server-only"` — 클라 번들에 못 들어감)

| 파일 | 담당 |
|---|---|
| `lib/space.ts` | `getSpaceConfig`, `getMyOrbitState`, `settleIdleCollection`(자동수거 정산 — ⚠️ 이슈 #31) |
| `lib/game-config.ts` | DB 설정 조회 + `config-specs` 폴백 적용 |
| `lib/rankings.ts` | 랭킹 뷰 조회 — 비캐시 원본(`fetchRankings`) + `React.cache` 래퍼(`getRankings`) 2층 |
| `lib/profile.ts`, `lib/launch.ts`, `lib/joops.ts` | 내 줍스/청약/스냅샷 조회 |
| `lib/supabase/{server,session,admin}.ts` | 3종 클라이언트 — anon(공개 읽기)/쿠키 세션/service_role(RLS 우회) |
| `lib/admin/*` | 관리자 세션(HMAC 쿠키)·인증·레이트리밋·초대코드 생성 |
| `lib/i18n/dictionaries.ts` | 사전 로더 — **en.json 이 타입의 진실**(04 문서 참고) |

### ③ localStorage 계층 (클라 전용, DB 없이 동작)

| 파일 | 키 | 담당 |
|---|---|---|
| `lib/debris-kinds.ts` | `joop03.debrisKinds.v1` | 종류별 수거 누적 — **이 관용구의 원형** |
| `lib/launch-replay.ts` | `joop03.lastLaunch.v1` | 발사 기록(다시 보기) |
| `lib/sound-prefs.ts` | `joop03.sound.v1` | 음소거 설정(같은 탭 즉시 반영 이벤트 변형) |
| `lib/ad-docks.ts` | `joop03.adDocks.v1` | 도킹한 광고 위성 + 서버 발급 초대코드 캐시 |

네 파일이 전부 같은 패턴(원문 문자열 스냅샷 + `useSyncExternalStore` 어댑터 + `v:1` 버저닝)을 따릅니다 — 상세는 04 문서.

## 4. components/ — 서버 / 클라이언트 구분

파일 첫 줄에 `"use client"` 가 있으면 클라이언트 컴포넌트(브라우저에서 실행), 없으면 서버 컴포넌트(서버에서만 렌더, JS 번들 미포함)입니다.

**서버 컴포넌트** (정적 표시 위주): `orbit-status`(궤도 4셀), `cleanup-gauge`(청소 게이지), `ranking-list`(랭킹 테이블 — 클라에서도 재사용 가능하게 "use client" 없이 순수하게 작성), `sparkline`, `debris-icon`(CSS 로 시트 크롭).

**클라이언트 컴포넌트 — 캔버스 게임 4형제** (각각 자체 rAF 루프 소유):

| 파일 | 화면 | 특징 |
|---|---|---|
| `orbital-canvas.tsx` | 첫 화면·지도의 지구본 | 줍스 100개 궤도 보간, 오프스크린 지구 캐시, deps `[]` + ref 다리의 교과서 |
| `orbit-track-map.tsx` | 지도의 equirectangular 궤적 모니터 | 육지 비트 그리드 1회 렌더, 밤 반구, ⚠️ "CSS transform 은 캔버스 rect 를 어긋낸다" |

## 6. 관리자 콘솔 — 3층 보안

`lib/admin/auth.ts` 의 주석이 이 구조를 가장 잘 설명합니다. 요지:

1. **`(protected)/layout.tsx` 의 가드** — 브라우저 진입을 막는다. 하지만 클라이언트 내비게이션에서는 레이아웃이 재실행되지 않는다.
2. **각 page 의 가드** — 위 구멍을 메운다.
3. **모든 mutation 서버 액션의 첫 줄 `requireAdminAction()`** — **보안상 유일하게 필수인 층.** Server Action 은 화면 렌더를 거치지 않고 POST 로 직접 호출될 수 있기 때문입니다.

같은 이유로 `proxy.ts`(라우팅 프록시)는 관리자 인증을 하지 않습니다 — matcher 에서 `/admin` 이 제외돼 있어 프록시를 아예 타지 않습니다. **"미들웨어에서 인증했으니 안전하다"는 가정은 이 구조에서 성립하지 않는다**는 것이 교훈입니다.

로그인 자체도 볼거리입니다: 성공/실패 응답 시간을 동일하게 맞춘 타이밍 오라클 방지, HMAC 서명 쿠키(비밀번호를 바꾸면 서명 키가 바뀌어 전 세션이 무효화되는 설계), 인메모리 레이트리밋("서버리스에서는 인스턴스별 메모리라 약한 방어"라고 **한계를 주석으로 정직하게** 명시).

## 7. proxy.ts — 미들웨어가 아니라?

⚠️ 이 커스텀 Next 16 에서는 `middleware.ts` 가 **`proxy.ts` 로 개명**됐습니다(Node 런타임 전용). 하는 일은 하나 — URL 에 로케일이 없으면 붙여서 리다이렉트:

1. `NEXT_LOCALE` 쿠키 → 2. `Accept-Language` 헤더(라이브러리 없이 q값 파싱) → 3. 기본값 `en`

matcher 정규식에 `admin$|admin/` 두 갈래가 있는 이유(주석): `/administrator` 같은 경로까지 제외되지 않게 하려고. 이런 "왜 이렇게 썼나" 주석이 이 저장소의 문화입니다.

## 8. 배포 흐름 (docs/infra.md 요약)

- Vercel **Hobby 플랜은 조직 소유 private 저장소의 Git 연동을 지원하지 않아** 원래 수동 배포였으나, 현재는 저장소가 public 이라 PR 을 올리면 프리뷰가 자동 배포됩니다.
- **배포 전 버전 범프가 중요합니다** (`package.json` version): ① 화면 우하단 버전 배지로 "지금 뜬 게 새 버전인지" 확인 ② `/api/version` 폴링이 이 값을 보고 **PWA 사용자에게 업데이트 배너를 띄웁니다.** 버전을 안 올리면 배포해도 사용자가 새로고침을 안 합니다.
- DB 마이그레이션은 CI 가 아니라 **사람이 Supabase 콘솔에서 수동 적용**합니다. PR 에 마이그레이션이 포함되면 본문에 명시하는 관행.
