## Q19. 에러·로딩 경계 세우기 ⭐⭐ (#32) 👈 안정성 첫 퀘스트 추천

**왜**: 이 저장소에는 `error.tsx` / `loading.tsx` / `not-found.tsx` / `global-error.tsx` 가 **하나도 없습니다.** 게임 페이지가 전부 `force-dynamic`(매 요청 DB 조회)이므로, Supabase 가 한 번 기침하면 첫 화면부터 **아무 설명 없는 500 백지**가 됩니다. 또 Suspense 가 없어 페이지 이동 중 화면이 굳은 것처럼 보입니다.

**파일**: `app/[lang]/error.tsx`, `app/[lang]/loading.tsx`, `app/[lang]/not-found.tsx` (신규 3개 — App Router 의 파일 규약), dict.

**힌트**:
1. Next.js 규약: 세그먼트에 `error.tsx`("use client" 필수, `{ error, reset }` props)를 두면 하위 렌더 에러를 잡아 폴백 UI 를 보여줍니다. `loading.tsx` 는 자동 Suspense 폴백.
2. 톤을 게임 세계관으로: 에러 = "교신 두절 — 재시도" (reset 버튼), 로딩 = CRT 스캔라인 위 "궤도 동기화 중…" + 줍스 스프라이트. `crt-brackets` 토큰 재사용.
3. `app/admin/` 트리에도 최소한의 error.tsx(한국어, 세계관 불필요)를 별도로 — 다중 루트 레이아웃이라 공유되지 않습니다(01 문서 §2).
4. dict 키는 en 먼저. 에러 화면 자체가 dict 로드에 실패할 수 있으니 **폴백 하드코딩 문구**를 병기하는 방어까지 하면 완벽합니다.

**검증**: 환경변수를 지운 로컬에서 첫 화면 진입 → 흰 화면 대신 "교신 두절" 화면이 뜨는지. 이 문서에서 유일하게 **로컬에서 완벽히 재현·검증 가능한** 퀘스트입니다.

## Q20. 발사 청약 가드 — 영구 갇힘 버그 ⭐⭐⭐ (#29)

**왜**: `bookLaunch` 에 상태 가드가 없어서 세 가지 사고가 가능합니다: ① orbit 줍스가 URL 직접 접근으로 청약 → 확정되면 **궤도에서 queued 로 강등**(첫 화면 집계에서 사라짐) ② 여러 발사체에 동시 확정 → `maybeSingle()` 이 multiple rows 로 죽어 **발사 영구 불가** ③ 정원 초과. "내 계정이 고장났다"는 최악의 이탈 사유입니다.

**파일**: `app/[lang]/launch/actions.ts` 의 `bookLaunch`, 관리자 확정 액션(`app/admin/(protected)/launch/`), `lib/launch.ts`.

**힌트**:
1. 클라 화면 숨김은 방어가 아닙니다(04 문서 §5 — Server Action 은 직접 POST 가능). **액션 안에서** `status !== "ground"` 거부.
2. 중복 확정 방어는 DB 가 제일 확실합니다: "confirmed 상태의 booking 은 owner 당 1개" — 부분 유니크 인덱스(`create unique index ... where status = 'confirmed'`) 마이그레이션 1개면 경쟁 조건까지 원천 차단.
3. 이미 발생한 다중 확정 데이터의 방어로 `lib/launch.ts` 가 `.limit(1)` 을 쓰고 있습니다 — 인덱스를 넣으면 이 방어 주석도 갱신하세요.
4. 정원: 확정 수를 세는 조건부 UPDATE 또는 확정 시점 재검증. 낙관적 동시성 관용구 적용.

**검증**: 프리뷰에서 orbit 계정으로 청약 API 직접 호출(curl) → 거부 확인. 부분 유니크 인덱스는 SQL 로 중복 삽입 시도.

## Q21. 온보딩 경쟁 조건 ⭐⭐⭐ (#30)

**왜**: `redeemInvite` 가 "익명 세션 생성 → 코드 소진" 순서라, 동시 사용 시 **소진 경쟁에서 진 쪽도 세션을 이미 들고 있어** setup 으로 직행 → 코드 없이 분양됩니다. 초대 코드가 보상(12 문서 Q18)과 연결되는 순간 이 구멍은 어뷰징 루트가 됩니다.

**파일**: `app/[lang]/onboarding/actions.ts`.

**힌트**:
1. 순서 뒤집기가 본질: **코드 소진(조건부 UPDATE + 갱신 행 확인)을 먼저**, 성공한 경우에만 세션 생성. 소진했는데 세션 생성이 실패하는 역방향 사고는 코드 status 를 되돌리는 보상 트랜잭션(또는 "소진됐지만 미사용" 상태 재활성화 로직)으로.
2. 이름 유니크 경쟁(#30-3)은 setup 액션에서 23505 를 `{error:"taken"}` 으로 번역하는지 확인 — 되어 있으면 문서화만.
3. 이 액션은 게임의 정문입니다. 수정 후 worklog 에 흐름도를 남기면 뒤에 오는 사람이 고맙습니다.

**검증**: 같은 코드로 동시 요청 2발(스크립트) → 한쪽만 성공, 다른 쪽은 invalid, 세션 잔류 없음.

## Q23. status 를 유니온으로 좁히기 ⭐⭐ (#36-4)

**왜**: `MyJoop.status` 가 `string` 이라 `"orbit "` 같은 오타가 컴파일러를 통과합니다. DB 는 이미 체크 제약으로 4개 값을 강제하는데 타입이 못 따라가는 상태.

**파일**: `lib/profile.ts`(타입 정의), 사용처 전체(tsc 가 알려줌).

**힌트**:
1. `export type JoopStatus = "ground" | "queued" | "launching" | "orbit"` 선언 후 `status: JoopStatus`. DB 값을 믿을 수 없다면 좁히는 파서(`isJoopStatus` 타입 가드)로 방어.
2. `npx tsc --noEmit` 이 어긋나는 비교·대입을 전부 나열해 줍니다 — **컴파일러를 리팩터링 체크리스트로 쓰는 경험** 그 자체가 이 퀘스트의 학습 목표입니다.
3. 11 문서 Q10(launching 활용)과 자연스럽게 이어집니다.

## Q24. 테스트 완화값 원복 체크리스트 ⭐ (문서 퀘스트)

**왜**: 개발 편의로 낮춰 둔 값들이 DB 에 남아 있습니다 — 정식 오픈 때 이대로면 밸런스가 무너집니다. 마이그레이션 주석에 *"정식 운영 전에 되돌려야 하는 값"* 이라고 적혀 있지만, 흩어져 있어 잊기 좋습니다.

**목록** (`supabase/migrations/20260727120000_...` 주석 + worklog):
