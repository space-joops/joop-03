# ADR-0004 · 인증 + 초대 코드 게이팅

- 상태: 제안됨(Proposed)
- 관련: FR-0.5, FR-2.1, FR-2.2, FR-9.1

## 배경 / 문제

- 첫 화면은 **로그인 없이 공개**(FR-1.1)지만, 줍스 분양은 **초대 코드**가 있어야 한다(FR-2.1). 이메일을 남기고 코드를 기다리거나, 친구 코드를 입력하면 시작.
- 로그인 시 본인 랭킹 등 개인화(FR-1.8)가 필요.

## 결정

- **Supabase Auth**를 신원의 근원으로 사용(공유 jd-04 프로젝트, [infra.md](../infra.md)).
  - 서버/클라 각각의 Supabase 클라이언트를 `lib/supabase/`에 둔다(`@supabase/ssr` 계열 패턴, 실제 패키지는 M0 구현 시 확정·설치).
  - 세션은 쿠키 기반. 서버 컴포넌트/route에서 세션 읽기.
- **초대 코드 게이팅**: `joop_03_invite_codes`로 관리.
  - 미가입자는 이메일 등록(대기) 또는 유효 코드 입력 시 가입·분양.
  - 코드 검증·소진(redeem)은 **서버(Server Action/route)** 에서만 수행, `service_role`로 원자적 처리(중복 사용 방지).
  - 발급자↔피초대자 관계를 저장해 활동 추적·보상(FR-6.5/9.2) 기반 마련.
- **인가(RLS)**: 개인 데이터는 `auth.uid()` 정책, 공개 데이터(첫 화면)는 anon SELECT 허용, 쓰기는 서버만. → [data-model](../data-model.md)

## 대안

- 자체 인증/제3자 OAuth 전용: 공유 Supabase를 이미 쓰므로 Supabase Auth가 자연스럽고 운영 부담이 적다.
- 코드 게이팅을 클라에서 처리: 위조 위험 → 서버 검증으로 결정.

## 영향

- M0에서 Supabase 클라이언트 유틸과 세션 헬퍼를 만든다(첫 화면 M1의 "로그인 시 내 랭킹"에 최소 세션 읽기 필요).
- 초대 코드 도메인 로직은 M2에서 본격화.
- 민감 키(`SUPABASE_SERVICE_ROLE_KEY`)는 서버 전용, 클라 노출 금지.

## 미해결

- 로그인 수단(매직링크/이메일+비번/OAuth) 확정.
- **초대 코드 형식·발급 한도·만료 정책.** 현재 시드 코드는 `JOOP-ALPHA-01` 형식(13자, 하이픈 포함)인데, M2 디자인 시안([handoff-m2.md](../../design/handoff-m2.md) §3-1)은 `[A-Z0-9]` **6자리 6칸 세그먼트 입력**을 전제한다. 코드 체계를 6자로 바꾸면 시안의 계기판 입력을 그대로 쓸 수 있고, 지금 형식을 유지하면 단일 콘솔 필드로 가야 한다(2026-07-27 디자인 적용 시점에는 후자를 택했다 — [워크로그](../../worklog/2026-07-27-m2-온보딩-디자인-적용.md)).
- `@supabase/ssr` 등 커스텀 Next 16 호환 검증.
