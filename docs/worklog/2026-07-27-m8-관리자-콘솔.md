# 2026-07-27 · M8 관리자 콘솔 (EPIC 10)

로드맵 **M8(운영)** 을 구현한 기록입니다. 요구사항의 EPIC 10(FR-10.1~10.3)과, EPIC 4에 있던
"관리자가 발사체 일정을 정하고 탑승 대상을 선별"(FR-4.2)이 대상입니다.

## 왜 지금 필요했나

요구사항에서 EPIC 10의 세 FR은 모두 우선순위가 「핵심」인데 로드맵에서는 맨 뒤(M8)로 밀려
있었습니다. 그 사이 운영자가 SQL 없이는 못 하는 일이 실제로 쌓였습니다.

- **게임 파라미터를 못 바꿨습니다.** `joop_03_game_config`에 키는 있었지만 편집 수단이 없었고,
  RLS 상 쓰기는 `service_role`만 가능했습니다.
- **더 나빴던 건, 바꿔도 안 먹었습니다.** `minigame_*` 6개 키는 DB에만 있고 게임은
  `lib/minigame.ts`의 `DEFAULT_CONFIG` 하드코딩을 쓰고 있었습니다. 편집 UI만 만들었다면
  "설정했는데 아무 일도 안 일어나는" 화면이 됐을 겁니다.
- **발사체 일정을 못 만들었습니다.** 5대가 M3 마이그레이션 시드로 박혀 있는 게 전부였습니다.
- **탑승 선별을 못 했습니다.** M3에서 자동 선별로 우회했고, `joop_03_launch_bookings`의
  `'rejected'` 상태는 스키마에만 있고 어떤 코드도 쓰지 않았습니다.
- **초대 코드를 못 발급했습니다.** M2 로그에 "초대 코드는 운영자가 발급"이라고 적었지만
  발급 화면이 없어 SQL을 직접 쳐야 했습니다.

## 무엇을 만들었나

`/admin` 아래 6개 화면입니다. 전부 한국어이고 데스크톱 기준으로 잡았습니다.

## 핵심 결정과 이유

### 인증: 왜 Supabase Auth가 아니라 환경변수 비밀번호인가

M2에서 게임 사용자는 **익명 세션**(`signInAnonymously`)으로 만들어집니다. 즉 "이 사람이
관리자다"를 식별할 수단이 아예 없습니다. `joop_03_profiles`에 `is_admin`을 붙이는 방법도
있지만, 익명 세션은 브라우저를 바꾸면 끊기므로 관리자가 기기를 옮기는 순간 권한을 잃습니다.
정식 로그인 수단은 [ADR-0004](../architecture/adr/0004-auth-invite.md)의 "미해결"로 남아 있어
거기에 기대면 이 작업이 그 결정을 기다려야 합니다.

운영자는 애초에 게임 플레이어가 아닙니다. 그래서 신원 체계를 분리해
**`ADMIN_PASSWORD` 환경변수 + HMAC 서명 httpOnly 쿠키**로 갔습니다. 게임 세션과 완전히
독립적이고, 지금 당장 동작하며, 관리자가 여러 명이 되면 `requireAdmin()` 하나만 갈아끼워
`joop_03_admins` 테이블로 승격할 수 있습니다.

서명 키는 `HMAC(ADMIN_SESSION_SECRET, sha256(ADMIN_PASSWORD))`로 유도합니다. 이렇게 하면
키 엔트로피는 시크릿에서 오고(비밀번호가 약해도 서명은 안전), 동시에 **비밀번호를 바꾸면
기존 세션이 전부 무효화**됩니다. 쿠키에 비밀번호 파생값이 실리지 않으므로 쿠키가 유출돼도
비밀번호를 역산할 수 없습니다. 시크릿 없이 비밀번호만으로 서명하면 쿠키 하나가
오프라인 크랙 오라클이 되기 때문에 피했습니다.

환경변수가 없으면 **fail-closed** 입니다. 로그인이 항상 실패할 뿐 아니라 기존 쿠키도
검증 불가로 거부되어 콘솔 전체가 잠깁니다.

### 가드를 세 겹으로 둔 이유

커스텀 Next 16 문서(`node_modules/next/dist/docs/.../layout.md`)에 이렇게 적혀 있습니다:

> Layouts do not rerender. They can be cached and reused...

즉 `/admin` → `/admin/config` 같은 클라이언트 네비게이션에서는 **레이아웃 가드가 다시 돌지
않습니다.** 그 사이 세션이 만료돼도 하위 페이지가 렌더됩니다. 그래서 각 페이지도 첫 줄에서
`requireAdmin()`을 부릅니다.

더 중요한 건 세 번째 층입니다. `proxy.md`가 명시합니다:

> Server Functions... are handled as POST requests to the route where they are used, so a Proxy
> matcher that excludes a path will also skip Server Function calls on that path. **Always verify
> authentication and authorization inside each Server Function.**

Server Action은 페이지 렌더 게이팅을 전혀 거치지 않고 POST로 직접 호출할 수 있습니다.
그래서 모든 mutation 액션이 첫 줄에서 `requireAdminAction()`을 부릅니다. 실제로 로그인 상태의
저장 요청을 그대로 캡처해 **쿠키만 빼고 재전송**해 봤고, 값이 바뀌지 않는 것을 확인했습니다.

페이지·레이아웃용(`requireAdmin`, redirect)과 액션용(`requireAdminAction`, null 반환)을 나눈
이유는 액션에서 `redirect()`가 예외를 던지면 `useActionState` 흐름이 깨지기 때문입니다.

### `/admin`을 i18n 밖에 둔 것 — 그리고 그게 만든 함정

관리자 콘솔은 운영자 전용 내부 도구라 10개국어 번역 대상이 아닙니다. 사전 파일이 관리자
문자열로 비대해지는 것도 피하고 싶었습니다. 그래서 로케일 없는 `/admin`으로 갔는데,
여기에 **반드시 걸리는 함정**이 두 개 있었습니다.

1. `proxy.ts`의 matcher가 로케일 없는 모든 경로를 `/{locale}/...`로 리다이렉트합니다.
   그대로 두면 `/admin`이 `/en/admin`으로 튕겨 화면에 도달조차 못 합니다. 더 나쁜 건
   **로그인 폼 제출(POST /admin/login)까지 리다이렉트되어 404가 난다**는 점입니다.
   matcher에 `admin$|admin/`를 제외 추가했습니다(`/administrator` 같은 경로는 계속 잡히도록
   두 갈래로 나눴습니다).
2. `app/`에 `layout.tsx`가 없고 `app/[lang]/layout.tsx`가 사실상 루트 레이아웃입니다.
   `/admin`은 그 밖이라 **자체 루트 레이아웃**이 필요합니다. Next 문서가 이 패턴을 명시적으로
   지원한다고 적고 있어(`app/dashboard/layout.js`와 `app/blog/layout.js`가 각각 루트가 되는 예)
   `app/admin/layout.tsx`에 `<html>`/`<body>`를 직접 렌더했습니다. 덤으로 게임의 PWA
   세로 고정 viewport를 상속하지 않아 데스크톱 화면을 자유롭게 짤 수 있었습니다.

가드는 루트 레이아웃이 아니라 `app/admin/(protected)/layout.tsx`에 둡니다. 루트에 두면
`/admin/login`까지 막혀 무한 리다이렉트가 납니다. 레이아웃은 pathname을 읽을 수 없으므로
(위 문서) "로그인만 예외" 처리가 불가능해서, 라우트 그룹으로 나누는 게 유일하게 깔끔한 방법이었습니다.

### 편집 UI보다 배선을 먼저 고쳤다

FR-10.2가 실제로 효과를 내려면 하드코딩 3곳을 먼저 걷어내야 했습니다.

- `components/ground-minigame.tsx`가 `DEFAULT_CONFIG`를 직접 쓰던 것을 `config` prop으로
  바꿨습니다. `useState(() => config ?? DEFAULT_CONFIG)`로 **마운트 시점에 고정**합니다.
  진행 중인 판은 설정이 바뀌어도 흔들리지 않고, 다시 들어와야 반영됩니다 —
  요구사항의 "설정값은 게임 재시작 시 반영"(FR-7.5/10.2)과 정확히 같은 의미입니다.
- `app/[lang]/joop/actions.ts`의 `XP_PER_DEBRIS = 8`, `MAX_DEBRIS_PER_RUN = 300`을 없애고
  서버가 config에서 읽어 XP를 계산합니다. 클라이언트는 여전히 "먹은 개수"만 보냅니다.
- `lib/joops.ts`가 config를 직접 조회하고 폴백 상수를 따로 들고 있던 것을 `lib/game-config.ts`로
  일원화했습니다. 폴백의 단일 진실은 이제 `lib/config-specs.ts`의 `spec.fallback`입니다.

`lib/minigame.ts`의 `DEFAULT_CONFIG`는 **지우지 않고 폴백으로 남겼습니다.** 순수 함수 모듈이라
서버·클라이언트가 함께 쓰고, M5 아케이드가 재사용할 예정이기 때문입니다.

### `orbital_tick_seconds`가 사실은 안 먹고 있었다

FR-10.1이 "좌표 계산 주기(기본 10초) 설정"인데, `app/api/orbital/route.ts`는
`export const revalidate = 10`이었습니다. 세그먼트 `revalidate`는 정적 분석 대상이라 리터럴만
쓸 수 있어서, **config를 아무리 바꿔도 서버 스냅샷 주기는 10초에 고정**이었습니다.
클라이언트 폴링 간격만 바뀌고 서버는 그대로였던 겁니다.

라우트를 `force-dynamic`으로 바꾸고 `Cache-Control: s-maxage=${tickSeconds}`를 직접 계산해
내보내도록 고쳤습니다. CDN이 그 시간 동안 응답을 고정하므로
[ADR-0005](../architecture/adr/0005-ssr-orbital-api.md)의 "N초마다 새 스냅샷" 설계는 그대로 두고
N만 설정을 따르게 됩니다. 실제로 config를 25로 바꾸니 응답 헤더가
`s-maxage=25`로 바뀌는 것을 확인했습니다.

### 자유 JSON 편집 대신 키 레지스트리

`value`가 jsonb라 자유 텍스트 편집이 제일 쉽지만, 오타 하나로 게임이 망가집니다
(`minigame_max_speed = 0` → 조작 불가, `minigame_fuel = -1` → 시작 즉시 종료).
특히 `minigame_xp_per_debris`는 `joop_03_joops.xp`가 int4라 **오버플로 벡터**입니다.

그래서 `lib/config-specs.ts`에 키별 라벨·설명·타입·min/max를 두고 서버에서 검증합니다.
`minigame_max_debris_per_run(≤5000) × minigame_xp_per_debris(≤1000) = 500만`이라 한 판 최대
XP가 int4 안에 넉넉히 들어옵니다. **이 두 키의 max는 함께 조정해야 합니다.**

`minigame_max_debris_per_run`은 이번에 새로 설정화한 키입니다. 연료를 크게 늘리면 정직한
플레이도 기존 상한 300을 넘겨 거부당하기 때문에, 함께 올릴 수 있어야 했습니다. 대신 이 키에는
"올릴수록 클라이언트 조작 여지가 커진다"는 경고를 화면에 붙였습니다.

레지스트리에 없는 키는 **읽기 전용으로 드러냅니다.** 숨기면 존재 자체를 모르게 되기 때문인데,
이 판단이 바로 쓸모가 있었습니다. 검증 중 DB에 `idle_collect_rate`, `idle_collect_cap_hours`,
`launch_countdown_seconds` 3개가 이미 들어 있는 걸 발견했습니다 — 공유 jd-04를 쓰는 다른
워크스페이스가 M4를 작업하며 넣은 것으로 보입니다. 공유 DB에서는 "내가 모르는 키가 이미
있을 수 있다"가 기본 전제여야 합니다.

### 선별에서 가장 조심한 것: 한 줍스가 두 로켓에 타는 문제

`joop_03_launch_bookings`의 unique는 `(vehicle_id, owner_id)`입니다. **발사체별로 1회**라는
뜻이지, 사용자가 발사체 하나에만 청약할 수 있다는 뜻이 아닙니다. 그래서 관리자가 A 로켓과
B 로켓에서 같은 줍스를 각각 승인하면 한 줍스가 두 로켓에 확정됩니다.

승인 시 "다른 예정 발사체에 이미 확정된 줍스인가"를 확인해 막았습니다. 반대로 거부·확정취소로
줍스를 지상(`ground`)으로 되돌릴 때도 **다른 예정 발사체에 남은 확정이 없을 때만** 되돌립니다.
그리고 되돌리는 UPDATE에는 항상 `.eq("status", "queued")`를 겁니다 —
이미 발사됐거나(`launching`) 궤도에 오른(`orbit`) 줍스를 지상으로 끌어내리면 안 됩니다.

정원 축소도 같은 성격입니다. 확정 인원보다 작은 정원으로 저장하려 하면 기본적으로 거부하고,
`force` 체크박스로만 허용합니다. **자동 강등은 넣지 않았습니다** — 누구를 내릴지는 정책
판단이고(신청 순? 레벨 순?), 코드가 임의로 정하면 안 되기 때문입니다. 대신 "정원 초과" 표시가
선별 화면으로 유도합니다.

### 마이그레이션 0건

새 테이블도 컬럼도 필요 없었습니다. `'rejected'`는 이미 스키마 check에 있었고, 초대코드·
대기리스트가 정책 0개로 `service_role` 전용인 것은 관리자 콘솔에 정확히 맞는 설계였습니다.
`updated_at`은 트리거 대신 액션에서 명시적으로 넣습니다 — 이 테이블에 쓰는 경로가 관리자
액션 하나뿐이라 트리거의 이점이 거의 없고, 공유 DB에는 객체를 하나라도 덜 만드는 게 낫습니다.

## 검증

`npm run build`, `npm run lint` 통과. 그리고 실제 브라우저(Chrome)로 종단 검증했습니다.

- 미인증으로 `/admin`, `/admin/config`, `/admin/launch`, `/admin/invites`, `/admin/waitlist`
  접근 → 전부 로그인 화면으로. `/`와 `/joop`의 로케일 리다이렉트는 그대로(회귀 없음),
  `/administrator`도 여전히 `/en/administrator`로.
- 틀린 비밀번호 거부(쿠키 미발급) → 맞는 비밀번호로 대시보드 진입.
  쿠키가 `HttpOnly`, `Path=/admin`, `SameSite=Lax`로 발급되고, **게임 페이지(`/ko`) 요청에는
  실려가지 않는 것**까지 확인했습니다.
- 서명을 1글자 위조한 쿠키 · 만료된 쿠키 · 쓰레기값 → 전부 거부.
- `ADMIN_PASSWORD`를 비우고 재기동 → 직전까지 유효하던 쿠키도 거부(fail-closed) + 경고 로그.
- 설정 저장 → 재조회로 DB 반영 확인. 브라우저의 `max` 속성을 걷어내고 범위 밖 값(999999)과
  정수 키에 소수(3.7)를 보내도 **서버가 거부**하고 DB가 오염되지 않음.
- `orbital_tick_seconds`를 25로 바꾸니 `/api/orbital` 응답이
  `Cache-Control: s-maxage=25` + `tickSeconds: 25`로 바뀜.
- 발사체 등록 → 목록 노출 → 취소 전환. 초대코드 2개 발급 → 폐기.
- **인증 우회 시도**: 로그인 상태의 저장 요청을 캡처해 쿠키만 빼고 재전송 → 값이 바뀌지 않음.
- 로그아웃 후 재접근 → 다시 차단.

검증용으로 만든 발사체와 초대코드는 공유 DB에서 삭제했고, 잠시 바꾼 설정값은 모두 원복했습니다.

## 알려진 한계 / 다음

- **정원 확정에 경쟁 조건이 남아 있습니다.** 확정 수를 세고 나서 쓰는 사이에 사용자 쪽 자동
  선별(`bookLaunch`)이 끼어들 수 있습니다. 이건 M3부터 있던 문제이고 관리자 승인 경로가
  늘면서 확률이 조금 커졌습니다. 정확히 고치려면 발사체 행을 `FOR UPDATE`로 잠그는 Postgres
  함수(`joop_03_confirm_booking`)가 필요한데, 이번엔 마이그레이션 없이 끝내기로 해서 넣지
  않았습니다. 실사용 규모(정원 수십, 운영자 1명)에서는 실질 위험이 낮지만 **없는 문제는
  아닙니다.**
- **로그인 시도 제한이 약합니다.** 10분 10회 인메모리 카운터인데, Vercel 서버리스는 인스턴스가
  여러 개라 우회 가능합니다. 실질 방어는 비밀번호 엔트로피입니다(랜덤 24바이트 권장).
  강한 방어가 필요해지면 DB 테이블이나 Vercel WAF로 옮겨야 합니다.
- 일괄 승인(레벨 순 자동 채우기), 발사체 삭제, 관리자 작업 감사 로그는 넣지 않았습니다.
- 관리자 계정이 하나(공유 비밀번호)입니다. 여러 명이 되면 `joop_03_admins` + 개인 계정으로.
- `scheduled → launched` 전환은 발사체 상태만 바꾸고 줍스는 건드리지 않습니다.
  줍스를 `launching`으로 올리는 건 M4(발사 시퀀스) 범위입니다.
