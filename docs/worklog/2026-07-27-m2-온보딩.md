# 2026-07-27 · M2 온보딩 (초대코드 · 분양 · 설정 · 인증)

로드맵 **M2 온보딩**을 구현한 기록입니다. 첫 화면(M1)에서 "초대코드로 시작하기"만 자리로 있던 것을, 실제로 **줍스를 분양받는 흐름**으로 연결했습니다.

## 무엇을 만들었나

미로그인 사용자가 **초대 코드**를 입력하면 세션이 생기고 줍스를 분양받아 이름·색을 정하는 온보딩, 그리고 초대 코드가 없으면 **이메일 대기리스트**에 등록하는 흐름입니다.

- 흐름: `/[lang]/onboarding`(초대코드/이메일) → `/[lang]/onboarding/setup`(이름·색) → 첫 화면에 "내 줍스" 표시.
- 데이터(공유 jd-04, `joop_03_` 접두사): `joop_03_profiles`(auth.users 확장), `joop_03_invite_codes`(테스트 코드 시드), `joop_03_waitlist`. 줍스 분양은 `joop_03_joops`에 `owner_id=본인`·`status='ground'`로 생성.

## 핵심 결정과 이유

### 인증은 "익명 세션 + 초대코드 게이팅"

요구사항은 이메일/초대코드 기반이지만, **매직링크(이메일 발송)** 는 공유 Supabase 프로젝트의 메일 인프라에 의존해 데모가 중간에 막힐 수 있습니다. 그래서 M2 MVP는 **Supabase 익명 인증**(`signInAnonymously`)으로 세션을 만들고, **초대 코드로 게이팅**했습니다. 확인 결과 이 프로젝트는 익명 인증이 이미 활성(`external_anonymous_users_enabled: true`)이라 추가 설정이 필요 없었습니다.

- 이메일 흐름(FR-2.2)은 **대기리스트 등록**으로 충족(초대 코드는 운영자가 발급).
- 정식 이메일/OAuth 로그인은 후속. 익명 세션은 나중에 계정 연동으로 승격 가능.

### 초대코드 검증·소진은 서버(service_role)에서만

초대 코드/대기리스트 테이블은 **RLS로 클라 직접 접근을 막고**, Server Action이 `service_role`(RLS 우회)로만 검증·소진·등록합니다(위조 방지). 코드 소진은 `status='active'` 조건부 UPDATE로 경쟁 조건(중복 사용)을 막았습니다. → [ADR-0004](../architecture/adr/0004-auth-invite.md)

### @supabase/ssr 도입 (커스텀 Next 16 async cookies)

M1에서 미뤘던 쿠키 세션을 도입했습니다. 커스텀 Next.js 16은 `cookies()`가 **async**라, `@supabase/ssr`의 `createServerClient`에 `getAll`/`setAll`을 async cookie store로 연결하고, **Server Component 렌더 중 set 은 try/catch로 무시**(쿠키 쓰기는 Server Action/Route에서만 가능)했습니다.

## 검증

- `npm run build` / `npm run lint` 통과. 온보딩 라우트 정상 생성.
- 마이그레이션은 공유 프로젝트라 M1과 동일하게 **Management API로 직접 적용**(초대코드 5개 확인).
- 실제 코드→분양→설정→내 줍스 표시 흐름은 배포 후 브라우저로 확인.

## 알려진 한계 / 다음

- 익명 세션이라 기기/브라우저가 바뀌면 세션이 이어지지 않음(계정 연동은 후속).
- 분양된 줍스는 `ground` 상태 — 랭킹(궤도) 진입은 지상 미니게임·발사(M3~) 후. 그래서 첫 화면 "내 랭킹"은 궤도 진입 이후 표시.
- 초대 코드 발급 UI(친구 초대, FR-9)·이메일 실제 발송은 후속.
