# 2026-07-26 · 디자이너 협업용 디자인 요청 문서 추가

요구사항 구조화(같은 날 PR #3)에 이어, **디자이너에게 실제 작업을 발주하기 위한 문서**를 추가했습니다. 왜 별도 문서가 필요했고 어떤 결정을 했는지 남깁니다.

## 무엇을 했나

`docs/design/` 아래 4개 문서를 만들었습니다.

- `design-brief.md` — 디자이너 발주용 요청서(목표·원칙·산출물·우선순위·제약·전달 방법·체크리스트)
- `design-tokens.md` — 카세트퓨처리즘 디자인 토큰 초안(색·타이포·간격·컴포넌트·모션)
- `asset-inventory.md` — 필요한 에셋 전체 목록(우선순위·포맷·사이즈·repo 경로)
- `README.md` — 에셋을 repo로 받을 때의 폴더 구조·네이밍·포맷·최적화 규칙

그리고 루트 `README.md` 문서 지도에 "디자인" 섹션을, `product/overview.md`의 카세트퓨처리즘 문단에 링크를 걸었습니다.

## 왜 별도 문서가 필요했나

기존 문서에도 카세트퓨처리즘 "방향"과 첫 화면 레이아웃 스케치는 있었지만, 그건 **개발/제품 관점**이었습니다. 디자이너가 그대로 읽고 착수하려면 (a)무엇을 만들지(산출물·우선순위), (b)어떤 제약인지(세로·PWA·다국어·Canvas 핸드오프), (c)결과물을 어떤 포맷으로 어디에 올릴지가 한곳에 정리돼야 합니다. 그래서 "요청서" 성격의 문서를 분리했습니다.

## 결정한 것들 (사용자와 함께)

1. **에셋은 repo에 직접 커밋** (Figma 등 외부 도구 링크가 아니라). → 그래서 폴더 구조(`public/design-src/` 원본 vs `public/` 산출물)·네이밍(kebab-case)·포맷 규칙을 문서로 못박음.
2. **문서 범위 = 브리프 + 토큰 초안 + 에셋 인벤토리** 3종(+관리 규칙 README).
3. **기존 PR #3에 얹기** — 새 PR을 파지 않고 요구사항 문서와 함께 리뷰·병합.

## 신경 쓴 정합성

디자인 문서가 기존 기술 결정과 어긋나지 않도록 링크로 묶었습니다.

- **Canvas 2D 핸드오프**(ADR-0003): 지구본·궤도·스파크라인은 이미지 파일이 아니라 "색·비율·선 두께 명세"가 핵심이라는 점, 스프라이트는 좌표 기준점·스프라이트시트가 필요하다는 점을 브리프와 인벤토리에 반영.
- **PWA 아이콘 세트**(ADR-0002): 192/512/maskable/apple-touch 180 + `app/icon.png` 파일 기반 API 위치까지 명시.
- **다국어**(ADR-0001): 언어별 텍스트 길이 편차·CJK/키릴 폰트 subset 주의를 원칙에 포함.
- **커스텀 Next.js 이미지 주의**: `next/image`의 `priority` deprecated(→`preload`), `minimumCacheTTL` 60s→4h를 에셋 최적화 규칙에 메모.
- **에셋 인벤토리 커버리지**: 첫 화면(M1) 스펙의 모든 UI 요소가 인벤토리에 1:1로 존재하는지 하단 표로 확인.

## 배운 점 / 다음 단계

- "방향 문서"와 "발주 문서"는 독자가 다르다 — 후자는 산출물·포맷·전달 경로가 자기완결적이어야 한다.
- 다음: 디자이너가 브리프대로 1순위(코어 토큰·브랜드/PWA 아이콘·첫 화면 시안)를 진행하고, 확정 토큰이 나오면 `app/globals.css`의 `@theme`(Tailwind v4)로 매핑하는 작업이 M0/M1에서 이어집니다.
