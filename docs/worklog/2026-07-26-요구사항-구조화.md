# 2026-07-26 · 이슈 #2 요구사항 구조화 (문서화)

GitHub 이슈 [#2 "요구사항-1"](https://github.com/space-joops/joop-03/issues/2)로 들어온 줍스 게임의 방대한 비전을, 곧바로 구현하지 않고 **먼저 문서 체계로 구조화**한 작업입니다. 왜 코드보다 문서를 먼저 만들었는지, 어떤 결정을 했는지 남깁니다.

## 무엇을 했나

이슈의 산문(우주 쓰레기 청소 게임 전체 비전)을 다음 문서로 나눠 정리했습니다.

- `docs/product/` — 개요, 요구사항 명세(11개 에픽 + FR 번호), 로드맵(M0~M8), 첫 화면(M1) 상세 스펙
- `docs/architecture/` — 데이터 모델(Supabase), 궤도 모델(좌표 공식), ADR 5종(i18n·PWA·Canvas2D·인증·SSR 궤도 API)
- `README.md`에 문서 지도 추가

## 왜 코드가 아니라 문서부터?

이슈 #2는 단일 기능이 아니라 **제품 전체**(인증·궤도 계산·랭킹·미니게임·발사·우주 지도·아케이드 물리·인벤토리·소셜·관리자)를 담고 있습니다. 현재 코드베이스는 백지에 가깝습니다. 이 상태에서 바로 구현하면 방향이 흔들리고 재작업이 생깁니다. 그래서 사용자와 합의해 **이번 산출물은 "명세 문서 + 로드맵"으로 한정**하고, 코드는 다음 단계로 미뤘습니다.

## 결정한 것들 (사용자와 함께)

1. **산출물 = 명세 + 로드맵 문서** (구현은 다음 단계).
2. **MVP 첫 조각 = 첫 화면**(궤도 도는 줍스 100개 + 랭킹). 로그인 없이 볼 수 있어 데모 임팩트가 크고, 동시에 이 제품에서 가장 독특한 기술 과제(서버 10초 좌표 스냅샷 + 클라 동일 공식 보간)를 초기에 검증할 수 있어서입니다.
3. **렌더링 = Canvas 2D 중심**. 요구 시각이 대부분 2D 투영이고 모바일 성능·난이도 면에서 3D 엔진은 과합니다. 필요한 효과만 나중에 부분 WebGL.

## 커스텀 Next.js에서 확인한 함정 3가지

AGENTS.md 규칙대로 `node_modules/next/dist/docs/`를 직접 읽고 검증했습니다. 표준 Next.js 습관대로 하면 틀리는 지점:

1. **`middleware.ts` → `proxy.ts`로 개명**(v16). 게다가 `proxy`는 **Node 런타임 전용, edge 미지원**. i18n 로케일 라우팅을 여기서 합니다.
2. **`next/image`의 `priority`가 deprecated** → `preload`/`fetchPriority="high"` 사용. 그래픽 많은 게임이라 중요.
3. **App Router에 내장 i18n 라우팅이 없음** → `proxy` + `[lang]` 세그먼트 + 서버 dictionaries를 직접 구성. 영어 폴백도 프레임워크가 아니라 우리가 `getLocale()`에서 처리.

추가로, 궤도 좌표 API는 현재 캐싱 모델(`cacheComponents` 미설정 = 레거시)에서 `export const revalidate = 10`이 정석이라는 것, `params`/`searchParams`가 Promise라 `await`해야 한다는 것도 확인해 ADR에 박아뒀습니다.
